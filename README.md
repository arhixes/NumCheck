# Архитектура: финансовый аналитик с проверкой чисел

## 1. Назначение и ключевая идея

Система отвечает на вопросы о финансовых показателях компании на естественном языке, например: «Как изменилась маржа в Q3 по сравнению с Q2?». Главное свойство системы: каждое число в ответе подтверждено и привязано к источнику.

Языковая модель не считает и не цитирует цифры по памяти. Она планирует шаги, вызывает детерминированные инструменты и формулирует ответ, а независимый верификатор проверяет все числа перед выдачей пользователю.

## 2. Принципы проектирования

1. Числа рождаются только в инструментах. Модель получает значения из вызовов, а не из собственной памяти.
2. Единый реестр результатов. Все вызовы инструментов записываются в него, и он служит единственным источником правды при проверке.
3. Верификатор независим от агента. Это детерминированный код без участия языковой модели, который не доверяет тексту, написанному моделью.
4. Отказ является корректным результатом. Если данных нет или вопрос построен на неверной посылке, система сообщает об этом, а не придумывает ответ.
5. Формулы метрик хранятся в коде. Модель выбирает метрику по имени, а запрос к данным строится программно.

## 3. Общий поток обработки запроса

1. Пользователь задаёт вопрос.
2. Классификатор вопросов определяет его тип, достаточность данных, неоднозначность и наличие ложной посылки. Неоднозначные вопросы получают уточнение, вопросы без данных получают отказ.
3. Агентный цикл передаёт вопрос языковой модели, которая последовательно вызывает инструменты.
4. Слой инструментов выполняет вызовы к данным и записывает каждый результат в реестр с уникальным идентификатором (r1, r2, r3 и так далее).
5. Когда данных достаточно, модель формирует черновик ответа с маркерами ссылок на записи реестра.
6. Верификатор проверяет все числа черновика по реестру и выносит вердикт.
7. При вердикте «повторить» список проблем возвращается модели, и она исправляет ответ. При вердикте «успех» ответ передаётся дальше. При вердикте «неудача» пользователь получает честное сообщение о невозможности подтвердить числа.
8. Модуль отображения ответа показывает текст, ссылки на источники и статус каждого числа.
9. Все данные поступают из слоя данных, на который опираются инструменты.

## 4. Компоненты

### 4.1. Слой данных и семантический слой

(не закончено) 

Поверх хранилища строится семантический слой. Он описывает метрики и измерения в виде конфигурации (YAML-файл), а не в виде текста для модели. Для каждой метрики указаны название, человекочитаемое описание, формула расчёта и единица измерения. Например, выручка определяется как сумма по статьям типа «выручка», а маржа как отношение разницы выручки и себестоимости к выручке. Измерениями служат направление, месяц, квартал и контрагент.

Модель выбирает метрику и измерения только по именам, а запрос формируется кодом. Это исключает ситуацию, когда модель «придумывает» собственную формулу показателя.

### 4.2. Слой инструментов

(не закончено)
1. query_metric получает значение метрики из семантического слоя за период с группировкой и фильтрами.
2. calculate выполняет арифметику над ссылками на записи реестра, а не над числами из текста. Благодаря этому производные значения тоже получают происхождение.
3. compare_periods возвращает абсолютное и относительное изменение показателя между двумя периодами.
   


### 4.3. Реестр результатов

Реестр хранит одну запись на каждый вызов инструмента. Запись содержит идентификатор, название инструмента, параметры вызова, значение, единицу измерения, период, список записей, из которых получено производное значение, и использованный SQL-запрос для аудита.

Таким образом реестр представляет собой граф происхождения чисел. На его основе работает верификатор и строится блок «как посчитано» в интерфейсе.

### 4.4. Классификатор вопросов

Это предварительный этап, который определяет, является ли вопрос аналитическим, есть ли необходимые данные, не слишком ли он общий («как дела?») и не содержит ли ложной посылки. Отдельный этап позволяет измерять качество отказов и уточнений независимо от остальной системы.

### 4.5. Верификатор чисел

Верификатор состоит из четырёх стадий, каждая из которых реализуется и тестируется отдельно.

1. Извлечение. Из текста ответа выбираются все числовые упоминания, включая форматы вроде «12,4 млн», «1 234 567 ₽», «15 %» и «в 2 раза».
2. Нормализация. Каждое число приводится к единому виду: значение, единица измерения и точность. Учитываются множители (тысячи, миллионы, миллиарды) и количество значащих цифр.
3. Сопоставление. Для каждого числа ищется соответствующая запись реестра с допуском, зависящим от точности записи. Если рядом стоит маркер ссылки, сначала проверяется именно он.
4. Семантические проверки. Производные числа пересчитываются по записям, из которых они получены. Сумма долей должна быть близка к 100 процентам. Слова «вырос» и «снизился» должны согласовываться со знаком изменения. Единицы измерения и периоды должны совпадать с заявленными.

Каждое число получает один из статусов: подтверждено, подтверждено как производное, не подтверждено или не совпадает с реестром. Общий вердикт принимает одно из трёх значений: успех, повторить с описанием проблем или неудача.

Из проверки исключаются годы, номера кварталов, порядковые числа и словесные количества вроде «два направления», иначе возникает много ложных срабатываний.

## 5. Пример обработки запроса

Вопрос: «Как изменилась маржа в Q3 по сравнению с Q2?»

1. Классификатор определяет, что вопрос аналитический и данные для него доступны.
2. Агент вызывает query_metric для маржи за Q3 и получает 31,2 процента (запись r1), затем для Q2 и получает 33,8 процента (запись r2). После этого вызывается compare_periods, и результатом становится снижение на 2,6 процентного пункта (запись r3).
3. Модель формирует черновик: маржа в Q3 составила 31,2 процента, что ниже 33,8 процента в Q2, снижение 2,6 процентного пункта, с маркерами ссылок на r1, r2 и r3.
4. Верификатор находит все три числа в реестре, пересчитывает разницу и убеждается, что слово «снижение» согласуется со знаком изменения. Вердикт: успех.

Если бы модель написала «снижение на 3 процентных пункта», верификатор отметил бы несовпадение с записью r3 (в реестре 2,6), вернул бы модели замечание, и она исправила бы ответ.
